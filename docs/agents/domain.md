# Domain Docs

Как инженерные скиллы должны использовать доменную документацию этого репозитория при исследовании кода.

## Перед исследованием прочитай

- **`GLOSSARY.md`** в корне репозитория, либо
- **`GLOSSARY-MAP.md`** в корне, если он есть: он указывает на отдельные `GLOSSARY.md` по контекстам. Читай те, что относятся к теме.
- **`docs/adr/`**: прочитай ADR, затрагивающие ту область, где собираешься работать. В multi-context репозиториях проверяй также `src/<context>/docs/adr/` на контекстные решения.

Если какого-то из этих файлов нет — **проходи молча**. Не подсвечивай их отсутствие и не предлагай создать их заранее. Скилл `/domain-modeling` (доступен через `/grill-with-docs` и `/improve-codebase-architecture`) создаёт их лениво, когда термины или решения действительно появляются.

## Структура файлов

Репозиторий этого проекта — single-context:

```
/
├── GLOSSARY.md
├── docs/adr/
│   ├── 0001-event-sourced-orders.md
│   └── 0002-postgres-for-write-model.md
└── apps/  packages/   ← вместо src/
```

Если однажды появится `GLOSSARY-MAP.md` в корне, репозиторий становится multi-context: решения уровня системы остаются в `docs/adr/`, а контекстные глоссарии и ADR живут рядом с контекстом (`apps/api/GLOSSARY.md`, `apps/api/docs/adr/`).

## Используй словарь глоссария

Когда твой результат называет доменное понятие (в названии issue, предложении рефакторинга, гипотезе, имени теста), используй термин так, как он определён в `GLOSSARY.md`. Не уходи в синонимы, которые глоссарий явно избегает.

Если нужного понятия в глоссарии ещё нет — это сигнал: либо ты придумываешь язык, которого в проекте нет (подумай ещё раз), либо это реальный пробел (заметь его для `/domain-modeling`).

## Подсвечивай конфликты с ADR

Если твой результат противоречит существующему ADR, скажи об этом явно, а не переопределяй молча:

> _Противоречит ADR-0007 (event-sourced orders), но стоит переоткрыть, потому что…_
