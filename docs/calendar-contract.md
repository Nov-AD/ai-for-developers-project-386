# Design-first граница календаря (#8)

Канонический контракт — [`packages/contract/main.tsp`](../packages/contract/main.tsp).
Правила времени, конкурентности, сортировки, валидации и обработки ошибок входят
в его описания и попадают в OpenAPI. Схемы, SDK, query-хелперы и серверные типы
генерируются; их нельзя исправлять вручную.

## Операции

| Операция SDK | HTTP | Успех |
| --- | --- | --- |
| `getHealth` | `GET /health` | 200, прежний `{ "status": "ok" }` |
| `listMeetingTypes` | `GET /meeting-types` | 200, JSON-массив; исходно `[]` |
| `createMeetingType` | `POST /meeting-types` | 201, сохранённый тип встречи |
| `getAvailability` | `GET /availability?meetingTypeId=<UUID>` | 200, границы окна и слоты |
| `createBooking` | `POST /bookings` | 201, сохранённая запись с типом встречи |
| `listUpcomingBookings` | `GET /bookings` | 200, JSON-массив предстоящих записей |

Точные поля и ограничения см. в TypeSpec, а не в отдельно поддерживаемых интерфейсах.
Например, окончание вычисляет сервер, `Booking.meetingType` содержит полное представление
типа встречи, а `windowEndDate` — исключительная **календарная дата владельца**.
HTTP 400 `INVALID_SLOT` означает недопустимый/устаревший выбор расписания; HTTP 409
`SLOT_CONFLICT` — пересечение записи. Их нельзя объединять в одну ошибку формы.

## Примеры как проверяемые HTTP-подмены

Каждая операция в TypeSpec содержит `x-contract-scenarios`: именованные взаимодействия
с `request.query`/`request.body`, ожидаемыми `status` и `body`. `requestValid: false`
помечает намеренно некорректный запрос. Примеры включают пустые и непустые списки,
пустую доступность, создание, ошибки полей, неизвестные поля/параметры, неизвестный
тип встречи, устаревший выбор и конфликт. Идентификаторы и время примеров демонстрационные.

Для HTTP-подмен фронтенда следует читать эти значения из сгенерированного
`packages/contract/tsp-output/openapi3/openapi.yaml`, а не копировать их в новый
набор ручных DTO. Например, успешный ответ первого среза:

```ts
const scenario = spec.paths['/meeting-types'].get['x-contract-scenarios']
  .find(({ name }) => name === 'empty')
// Подмена HTTP-границы: scenario.status, scenario.body, Content-Type: application/json.
```

`apps/api/test/contract-design.test.ts` проверяет все эти запросы и ответы по
сгенерированным JSON Schema (Ajv 2020-12 с проверкой UUID/date/date-time), включая
соответствие статуса и машинного кода. Проверяются также стандартные OpenAPI-примеры,
созданные `@example`/`@opExample`. Негативные контроли доказывают, что валидатор
отвергает неверный статус, код ошибки и неполный ответ.

Важно для реализации серверной валидации: в OpenAPI 3.1 запрет лишних полей входных
моделей представлен `unevaluatedProperties: { not: {} }`. Генератор Zod 0.99.0
создаёт обычный `z.object`, который сам по себе удаляет лишние поля.
Обработчик обязан использовать строгую валидацию объекта (например, `.strict()`),
а не считать удаление лишних полей выполнением контракта. Контрактные сценарии
с `unknown-field` должны возвращать 400.

## Строгие сценарии сервера

`apps/api/test/contract.test.ts` по-прежнему требует реализации **каждой** операции
и запрещает маршруты вне контракта. Теперь операции проверяются по отдельности,
а HTTP-примеры становятся параметризованными сценариями. Данные подготавливаются
только через публичный API, на изолированном экземпляре приложения; системное время
фиксируется средствами Vitest, настройка окна — `tomorrow`. Вместо демонстрационных
UUID запросы используют UUID действительно созданных типов встречи.

Подготовка занятых слотов, непустых списков и полностью занятого окна уже описана
в тестовом helper, но до появления соответствующих маршрутов её работа с настоящим
сервером **не подтверждена**. Нет пропусков, allowlist недостающих операций, фиктивных
маршрутов или ослабления гейта. На этапе #8 сервер продолжает реализовывать только health.

## Порядок следующих срезов и свидетельства

### Создание типов встреч (#10)

Страница `/owner` открывается напрямую и через навигацию «Владельцу». Форма создаёт
тип встречи через `POST /meeting-types`; список обновляется через TanStack Query.
На `/book` гость видит название, описание и длительность и выбирает один тип встречи.
Доступность и создание записи относятся к следующим срезам и пока не предоставляются.

**Раздел владельца и API не защищены авторизацией: данные доступны каждому,
кто обращается к приложению.** Это не защищённый личный кабинет. Не используйте
реальные персональные данные даже в демонстрации.

Хранилище находится в памяти одного экземпляра приложения. **Перезапуск очищает
и типы встреч, и записи**; несколько процессов/инстансов не поддерживаются.
Новый экземпляр начинает с пустого списка. Названия обрезаются по краям,
описание сохраняется как введено (при отсутствии — пустая строка), длительность
может быть любым целым числом от 1 до 540, не только кратным 30.
Эти предупреждения также показаны на странице владельца.

### Проверки и оставшийся граф

Граф: **#8 → #9 → #10 → #12 → #13 → #14**, отдельно **#9 → #11** (release-please).
Вся последовательность идёт в `feat/calendar-spec-7`; временный красный контрактный
гейт не разрешает слияние незаконченной функциональности в основную ветку.

Первая функция #9 — только реальный репозиторий → `GET /meeting-types` → SDK →
страница `/book`, включая исходный пустой список. Создание типа встречи — следующий
срез #10. Генерация и проверки для каждого тикета:

```bash
mise run codegen
# Диагностика звеньев:
pnpm contract:build
pnpm sdk:build
pnpm api:types
pnpm --filter @calendar/sdk build
pnpm --filter @calendar/api exec vitest run
pnpm --filter @calendar/web exec vitest run
mise run check
```

Повторная генерация должна оставлять артефакты неизменными. Изменения API проходят
через TypeSpec, проверку совместимости `mise run contract:breaking`, затем генерацию
и адаптацию обеих реализаций.

При #9 после `mise run dev`:

```bash
curl --fail-with-body --include http://127.0.0.1:3000/meeting-types
```

Ожидание: HTTP 200, JSON Content-Type, `[]` из пустого настоящего хранилища.
В реальном браузере открыть `http://127.0.0.1:5173/book`, сверить фактический запрос,
ответ API и пустое состояние. Ни HTTP-подмен, ни демонстрационных констант в этом
браузерном свидетельстве нет. После #10 повторить с непустым списком; затем добавить
выбор слота, сохранение имени, подтверждение, страницу владельца, конфликт двух гостей
и восстановление после ошибки. Недоступный браузер — блокировка, а не успех.

При #13 отдельно выполнить ровно один тест:

```bash
pnpm --filter @calendar/api exec vitest run -t 'rejects overlapping bookings across meeting types'
```

Доказать чувствительность: зелёный → временно нарушить только серверный запрет
пересечений разных типов → ожидаемый красный (201 вместо 409) → восстановить своё
изменение → зелёный. Ожидания теста и контракт не менять; затем API-тесты и полный гейт.

Release-please (#11) настраивается после первой работающей функции: один релиз
приложения, без публикации workspace-пакетов. Проверка реального workflow и разрешений
не подменяется проверкой YAML. До окончания #14 полный гейт должен стать зелёным.
Этот документ фиксирует план проверок, **не утверждает их функциональное прохождение**.
